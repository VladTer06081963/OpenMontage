# 004 · Реализовать `mode="job"` для тяжёлых генераций

**Дата:** 2026-10-25 · **Штамп:** long-jobs · **Аудит:** [A004](../audit/004_long-jobs_2026-10-25.md)

## Цель
Платная долгая задача не должна оборваться по клиентскому таймауту и не должна быть оплачена дважды.

## Что сделать
1. `om_tool_run(..., mode="sync" | "job")`; порог автоматического переключения —
   `BaseTool.dry_run().estimated_runtime_seconds` > ~60 с.
2. Фоновый вызов в thread-пуле; метаданные задачи —
   `projects/<id>/artifacts/jobs/<job_id>.json`, запись атомарная через `provider_jobs.save_job`.
3. Тул `om_job_status(job_id)` → `running | completed | failed`; `om_job_result(job_id)` → результат,
   пути, `cost_usd`, `model`, `seed`.
4. Бюджет: `reserve()` **до** старта задачи, `reconcile()` — по её завершении.
5. Идемпотентность: повторный вызов с теми же `params` возвращает тот же `job_id`
   (`BaseTool.idempotency_key`), а не создаёт вторую оплату.
6. Ошибка опроса не должна приводить к повторной отправке запроса (семантика `poll()`).

## Готово, когда
- [ ] долгий тул в режиме `job` возвращает `job_id` мгновенно — тест
- [ ] повторный вызов с теми же `params` не плодит задачи и не списывает бюджет дважды — тест
- [ ] `om_job_status` даёт `running → completed` и финальный `cost_usd` — тест
