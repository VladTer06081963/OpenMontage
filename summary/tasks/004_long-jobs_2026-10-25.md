# 004 · Реализовать `mode="job"` для тяжёлых генераций

**Дата:** 2026-10-25 · **Штамп:** long-jobs · **Аудит:** [A004](../audit/004_long-jobs_2026-10-25.md)
**Статус:** ✅ выполнено

## Цель
Платная долгая задача не должна оборваться по клиентскому таймауту и не должна быть оплачена дважды.

## Что сделано

| Файл | Что |
|---|---|
| `lib/mcp_bridge.py` | `tool_run(..., mode="auto\|sync\|job")`, `_spawn_job()`, `job_status()`, `job_result()`, `job_list()`, `_estimated_seconds()` |
| `scripts/mcp_job_worker.py` | **отсоединённый воркер**: выполняет тул ровно один раз, сверяет бюджет, пишет результат в job-запись |
| `tools/cost_tracker.py` | добавлен `reload()` — чтобы мост и воркер не затирали состояния друг друга |
| `scripts/openmontage_mcp.py` | тулы `om_job_status`, `om_job_result`, `om_job_list`; `om_tool_run` получил параметр `mode` |
| `tests/lib/test_mcp_bridge_jobs.py` | 9 тестов на настоящем тулe в настоящем подпроцессе |

## Ключевые решения

- **Воркер — отдельный процесс** (`start_new_session=True`): переживает таймаут клиента
  **и** падение MCP-сервера. Это ключевое отличие от «просто долгий вызов в треде».
- **Job-запись — источник истины**: `projects/<id>/artifacts/jobs/<job_id>.json`,
  атомарная запись через `tools/provider_jobs.save_job`. Статус читается с диска,
  поэтому переживает перезапуск; после переподключения клиент находит задачи через
  `om_job_list`.
- **Идемпотентность**: ключ `tool:idempotency_key(params)`; повторный вызов с теми же
  параметрами возвращает **тот же** `job_id` с `idempotent_replay: true` — второй оплаты нет.
- **Бюджет**: `reserve()` до старта воркера, `reconcile()` по завершении (в воркере).
- **Режим `auto`**: `estimate_runtime() >= 60 с` → job. Fallback по capability
  (`video_generation`, `avatar`, `3d_*`, `music_generation`, `character_animation` → 120 с),
  потому что `estimate_runtime()` реализован не у всех тулов.
- **Порог настраивается**: `OPENMONTAGE_MCP_JOB_THRESHOLD_SECONDS` (по умолчанию 60).

## Известные ограничения

- Тул, зарегистрированный только в памяти процесса моста, воркер не увидит (тестовые
  заглушки); реальные тулы лежат в пакете `tools/` и находятся через `registry.discover()`.
- Параллельные записи в state-файл трекера из двух процессов не защищены блокировкой —
  окно узкое (reserve до старта, reconcile после), но при высокой параллельности возможен
  конфликт. Следующий шаг — файловая блокировка.
- Прогресс внутри задачи не транслируется (`ctx.report_progress` требует progress-token
  от клиента) — источник истины `om_job_status`.

## Проверено
- `pytest tests/lib/test_mcp_bridge_jobs.py` → **9 passed**
- задача завершается в отдельном процессе, результат и артефакты на месте (тест)
- повторный идентичный вызов → тот же `job_id`, `idempotent_replay: true`, одна запись (тест)
- `auto` переключается в job при пороге 0 и остаётся sync при пороге 3600 (тест)
- `dry_run` сообщает `would_use_job` и ничего не исполняет (тест)
- упавший тул → `status: failed` с текстом ошибки (тест)
- бюджет: запись `reserved` → после завершения `completed` (тест)
